# AGENTS.md

DeckGrade is a DeckyLoader plugin (Steam Deck / SteamOS) that adjusts display saturation, contrast, and vibrance, including per-game profiles keyed by Steam AppID. Frontend: React/TS via `@decky/ui` + `@decky/api`. Backend: pure Python (`main.py`), no compiled binaries — the template's `backend/` C demo was deliberately removed; do not reintroduce it.

## Architecture

- Frontend↔backend contract: `callable<Args, Ret>("method_name")` in `src/index.tsx` invokes public async methods of the `Plugin` class in `main.py`. Lifecycle hooks: `_main`, `_unload`, `_uninstall`. The `decky` module is injected by decky-loader at runtime; `decky.pyi` is the type stub, `py_modules/` is for extra Python deps (currently empty).
- react/react-dom are supplied by the decky-loader host at runtime, never bundled (hence `ignoreMissing` peer rules).
- Display control mechanism (the core of this plugin): gamescope hosts an XWayland server and reads X11 root-window properties even though SteamOS is Wayland. `main.py` drives them via `xprop`:
  - `GAMESCOPE_COLOR_SDR_GAMUT_WIDENESS` — CARDINAL holding a float bitcast (`struct pack/unpack`), vibrance 0.0–1.0. Same property SteamOS's native Color Vibrance writes; the 5s watchdog in `main.py` keeps the plugin's value authoritative while enabled.
  - `GAMESCOPE_COLOR_LOOK_G22` — string path to a generated `.cube` 3D LUT (format: `LUT_3D_SIZE n` + n³ triplets, R fastest, edge size 2–128). Saturation, contrast, shadows, and highlights are baked into one LUT written to `DECKY_PLUGIN_RUNTIME_DIR`. Gamescope only reloads the LUT on a property change, so the property must be re-set whenever the file is regenerated (even though the path is unchanged). Neutral settings → property removed. SDR only by design (no `GAMESCOPE_COLOR_LOOK_PQ`).
  - Gamescope detection: run `xprop -display :N -root` over candidates (`$DISPLAY`, `:0`, `:1`) and check the output for `GAMESCOPE_` root properties. Do NOT gate on `/tmp/.X11-unix/*` file existence or `/proc` comm scans — v0.1.0 did and false-negatived on a real Deck. A detection miss never blocks the UI; the watchdog keeps retrying and applies settings as soon as gamescope is reachable.
- Settings persist at `DECKY_PLUGIN_SETTINGS_DIR/deckgrade.json`; apply is debounced (~150ms) and forced once on explicit user changes (`force=True` path also restores defaults when disabled), while the watchdog only enforces when enabled.
- Settings model (v0.3.0+): top-level keys are the **global profile** (`enabled` + the five values) — v0.1/0.2 flat files are already valid; per-game profiles live in `"games": { "<appid>": { five values } }` (AppID as string key). `enabled` is a single master toggle. A v0.2 file loads untouched except that `games` defaults to `{}`.
- Per-game profile API: `set_value(target, key, value)`, `reset_profile(target)`, `copy_global_to("current")` with `target \in {"global","current"}` — "current" is **resolved server-side at call time** to the running game (never pass an AppID from the UI, it can be stale). `get_state()` returns `{enabled, global, games, app, active_profile, gamescope, display, xprop}`; `active_profile` is "game" when the running game has a stored profile. New game profiles are seeded as a **snapshot copy of the global profile** (first edit/reset/copy in a game with no profile) — snapshot semantics, no live linkage.
- Active-game detection (v0.3.0+): read the `GAMESCOPE_FOCUSED_APP_GFX` root property (32-bit CARDINAL base-layer AppID, exposed in Steam Mode only — exactly the mode we apply to; source: `steamcompmgr.cpp`, reference in `.opencode/research/`). Fall back to `GAMESCOPE_FOCUSED_APP` when absent. **Dashboard = AppID 769** (hard-assigned, `steamcompmgr.cpp:4849-4850`): treat 0/absent/769 as "no game" → global profile. Do NOT reintroduce `/proc` or `ps`-based detection (v0.1.0's file/comm gating false-negatived on a real Deck). All root reads (gamescope liveness, appids, wideness, look path) come from a **single `xprop -root` dump** per tick/action — no extra subprocesses.
- When the resolved game/profile identity changes, the watchdog emits `deckgrade_state_changed` via `decky.emit` (state dict as the only payload; no `decky` module is available in the frontend — use `addEventListener`/`removeEventListener` from `@decky/api` with exact event name). The UI also re-fetches `get_state` after each user action (values may have been clamped server-side).

## Gotchas

- TS type errors do NOT fail `pnpm run build` — rollup prints them as warnings and still emits `dist/index.js`. Read build output for `TS####` warnings; don't trust exit code alone.
- `@decky/ui` `SliderField` has `disabled`/`editableValue`/`valueSuffix` props; there is no `editable` prop. Check `node_modules/@decky/ui/dist/components/*.d.ts` for exact props before using components.
- `plugin.json` `flags` must stay `[]` (runs as `deck` user). Do not add `_root`: xprop access to gamescope's X server works unprivileged, and root changes the runtime home/env assumptions.
- Keep black at (0,0,0) in generated LUTs: a raised black floor flips gamescope's overlay alpha handling (`bRaisesBlackLevelFloor`).
- `_load_settings`/`_save_settings` in `main.py` **must preserve the `games` map**: loading used to drop unknown keys, and the first save after a v0.3.0 upgrade would have silently wiped all per-game profiles. The LUT cache is a single value keyed by the (saturation, contrast, shadows, highlights) signature — pure function of values, so it is safe to share across profiles; the look property is re-set whenever the signature changes even if the path is identical.
- Version lives in `package.json` (`version`), display name/author in `plugin.json`; the zip filename and README install path reference the version — bump them together.
